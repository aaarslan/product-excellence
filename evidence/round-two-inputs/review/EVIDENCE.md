# Pickup substitution flow

A regional grocer offers scheduled pickup. At checkout, shoppers choose “No substitutions” or “Suggest replacements,” defaulting to the latter. The accompanying text says “We'll ask before making a change.” Shoppers can record item-specific notes such as brand preferences. This review covers ordinary groceries; age-restricted products cannot be substituted through this flow.

When a picker proposes a replacement, the app sends a push notification and displays an order banner. The replacement screen shows the original item's photo, replacement name and unit price, and Accept/Decline buttons. It does not show the original unit price, replacement package size, or resulting line total until a separate detail view. Availability data already contains those fields. Customers may accept, decline, or select an alternative from current inventory. An alternative creates a new request for the picker, who must confirm availability.

The picker can wait three minutes. With no response, the system automatically accepts the suggested replacement unless the item has a “No substitutions” flag. The checkout promise does not mention this timeout. Customers cannot extend the waiting period. Backend status is authoritative, but a screen opened before the deadline can still show enabled buttons after the system accepts; a late Decline returns “Order updated” even when the item was already packed. The event log distinguishes these outcomes; the client does not.

Over two weeks there were 1,200 replacement proposals: 510 explicit accepts, 190 explicit declines, and 500 timeouts. Push receipt is not measured. A timeout does not establish that the shopper saw the proposal. Twenty-three support contacts mentioned unexpected replacement cost; 11 mentioned a decline not taking effect. Contacts may overlap and do not measure the total number of dissatisfied shoppers. Pickers report that extending all waits would put pickup slots at risk, but there is no measured estimate of that delay.

Five usability sessions found that four shoppers compared package sizes before choosing, and three interpreted “We'll ask” as requiring their explicit consent. These sessions did not involve actual time pressure. The business wants fewer complaints without increasing out-of-stock refunds. Automatically declining all timeouts could reduce unexpected charges but increase missing items. Continuing automatic acceptance preserves fulfillment but leaves the consent expectation unresolved.

Budget: one frontend engineer and one designer for five working days. They can change disclosure, display existing price/size data, and consume the existing authoritative status endpoint. Changing picker scheduling or default timeout behavior needs backend and operations work unavailable this sprint. Product may recommend that follow-up, but should not represent it as delivered. No current evidence establishes which single intervention will reduce support contacts most.
